Introduction · Context of the project

What we set out to build.

Rocket Elevators is an operations dashboard and data pipeline that analyzes the status of Ontario's elevator fleet. The whole project was built with an AI‑assisted workflow — spec‑first, reviewed on every change, and shipped as a small set of independent services.

The domain

Ontario's TSSA‑regulated elevating devices — licenses, inspections, incidents, and alterations.

The user

An operations manager who needs fleet status, compliance risk, and safety history at a glance.

The goal

One operational picture, plus a natural‑language assistant to help understand what's on screen.

Introduction · The problem

The data was true, but unusable.

Everything the operations team needed already existed — scattered across five separate government datasets that didn't share a clean key, a date format, or a single source of truth.

Data Processing · Data preprocessing

Making five datasets agree.

Most of the real work is cleaning. Every transform is deliberate and documented, so the same input always produces the same database.

  • Status filter — keep only ACTIVE and BY REQUEST devices (45,383 → 43,002)
  • Key normalization — every dataset's device number cast to one integer elevator_id
  • Location validation — drop 75 rows where license and installed records disagree
  • Date parsing — many formats normalized to YYYY‑MM‑DD
  • Deduplication — keep only the most recent inspection per elevator
  • Column collapsing — ~30 sparse injury flags reduced to one injury_severity value
Data Processing · NLP

Turning 2,446 incident stories into priorities.

Incident narratives are short — about 12 words each — so we cleaned them with NLTK and used TF‑IDF + K‑means rather than topic modelling, which needs longer text. The clusters consolidate into four hazard families.

Data Processing · ML

Predicting which inspections will fail — honestly.

A Random Forest scores each elevator's failure risk from engineered inspection‑history and order‑risk features. It's evaluated on a time‑based split — trained on 2011–2015, tested on 2015–2017 — with every feature gated to data that pre‑dates the inspection, so there is no leakage.

  • Risk levels — HIGH ≥ 0.70 · MEDIUM ≥ 0.40 · LOW below
  • Plain‑English why — a language model turns each HIGH score into a short explanation grounded only in that elevator's record
  • Surfaced everywhere — table badge, alerts feed, and detail panel

Front‑end · The interface

A dashboard you operate, not a page you read.

HTMX 2 + Tailwind + Jinja2, and zero custom JavaScript. Every filter, sort, search, page, and chat turn is a server round‑trip swapped into place — the client holds no state.

Four pages

Overview, Fleet, Alerts, and Conversations — one persistent shell, only the main area swaps.

The instrument panel

Monospaced numerals everywhere; green / amber / red mean state, blue means interaction.

No‑JS visuals

A CSS conic‑gradient donut shows the risk split; status and outcome render as colored badges.

Front‑end · The assistant

One chat box, the right specialist.

A floating Fleet Assistant sits on every page. The user asks one way; behind the scenes the message is routed to one of four agents — the routing is invisible.

General

Definitions, terminology, and greetings — answered from the assistant's knowledge, no tools.

Data

Live fleet stats, lookups, inspection history, risk, and incidents — read from the database.

Knowledge

Procedural and technical questions answered from maintenance docs and incident narratives.

Scheduling

Books an inspection through a guarded, two‑step confirmation before anything is written.

Backend · Go API

The single source of truth.

A Go service on port 8080 over a pooled PostgreSQL connection. Every elevator, inspection, risk score, and conversation the dashboard shows comes from here — with parameterized queries, validated filters, pagination, and fleet‑wide aggregates.

Fast & typed

Compiled Go with the pgx driver; a 15‑second budget per request.

Safe by default

All filters validated; queries parameterized — no string‑built SQL.

Read & aggregate

Joins inspections and predictions per elevator; computes the fleet stats and alerts.

Backend · Flask

A thin renderer in front of Go.

Flask on port 5000 is the only thing the browser talks to. It turns the Go API's JSON into the HTML fragments HTMX expects — it does not own any fleet data.

One rendering rule

An HX‑Request check decides: full page shell on a direct visit, partial fragment on a swap.

Safe markdown

LLM replies become safe HTML — risk words turn into colored badges, field labels are bolded.

Proxy, not owner

Reads CSV only for incident & alteration counts in the detail panel; everything else is the Go API.

Backend · Chatbot

How a message becomes an answer.

The chatbot lives inside the Go API. A deterministic, keyword‑based classifier reads each message — no extra LLM call — and routes it to the right agent.

Scheduling is two‑phase: the model proposes, the user confirms, and only then is the write committed — protected by an HMAC signature and a 10‑minute expiry.

Backend · LLM

The language model, chosen by environment.

All four agents call one chat endpoint through a provider cascade, so the same code runs locally and in production without changes.

Provider cascade

Production runs on OpenRouter; when its key is absent the code falls back to Ollama cloud. Model and provider are picked from environment variables.

Numbers never hallucinated

For data answers, Go formats the exact figures and the model writes only the surrounding sentence — so a wrong number can't be invented.

The system prompt is embedded into the Go binary at build time and used verbatim, keeping the assistant's boundaries fixed.

Backend · RAG & MCP

Grounded knowledge, behind a guarded tool layer.

RAG

Two committed ChromaDB collections — maintenance_docs (six manuals, chunked and embedded with bge‑small‑en‑v1.5) and incident_narratives. The knowledge agent answers over what it retrieves, so replies cite real text.

Index committed with the repo · ~3 MB

MCP

A FastMCP server on port 8765 exposes 10 tools over JSON‑RPC — 7 read · 2 RAG · 1 write. Each agent has a strict allowlist, so the model can only do what it's permitted to.

The only path to live data and writes
